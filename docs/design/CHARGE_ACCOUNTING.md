# Measured charge accounting — B04 design

Status: Check-to-Check offline accounting is implemented for Toxic blowpipe and supported Trident variants on 2026-09-13; live client acceptance remains in B05. Trident charge/uncharge dialog reads and the optional “unmeasured” HUD balance are design inputs only and are not implemented. This design follows the project accounting rule: only measured item quantities create cost. A Check menu action supplies a short-lived target identity only; the numeric chat read supplies the measurement. Menu selections, animations and probabilities alone are not accounting evidence.

## Evidence and measurement

The source shape is pinned to [geheur/weapon-charges `ChargedWeapon.java`](https://github.com/geheur/weapon-charges/blob/70de60ae5c65c3a469fee386d994e6bd965c1c56/src/main/java/com/weaponcharges/ChargedWeapon.java) and its [plugin message parser](https://github.com/geheur/weapon-charges/blob/70de60ae5c65c3a469fee386d994e6bd965c1c56/src/main/java/com/weaponcharges/WeaponChargesPlugin.java). Trident Check messages report a comma-formatted charge count, literal `one charge`, or `no charges`; Blowpipe Check messages report dart type/count and scale count independently, or `Darts: None` plus scale count. The upstream Trident animation (`11430`) and Blowpipe animation ids (`5061`/`10656`) feed estimates only and are intentionally excluded from accounting.

Each exact Check response must match a fresh Check menu action. The click's widget, slot, item id and supported variant form an in-memory target identity; the click itself supplies no count. The same target identity must be present on both reads, so switching between two same-variant weapons or moving the item seeds a new baseline instead of comparing balances that may belong to different weapons. The first valid read only establishes the baseline. A later read can book only the negative difference in measured component quantities. Equal, increased, malformed, unsupported, or variant-switched reads update/reset display state without booking. A charge increase is not a cost read. The live item-on-item menu path supplies no amount, so its settled candidate component losses are removed from ordinary settlement and stored in one uncounted Ledger Review row with their original flows. A later Check for the same target can confirm a load: Blowpipe scale increases directly confirm only that many scales; blowpipe darts remain in Review because no dart-per-load quantity is inferred. Trident charge increases use the variant's documented measured components-per-charge recipe. A partial match becomes a neutral transfer for the confirmed quantity and leaves residual flows in Review. A Check without positive exact load evidence, a changed target, multiple candidate rows, or an expired 10-minute window leaves the row in Review for the owner; it is never converted into a cost automatically. The charge-spend guard blocks components that still have unresolved Review quantities (and components the owner explicitly chose to count), preventing overlap with measured depletion. Inventory deltas remain aggregated by item id, so same-id source attribution within one candidate settle is still a live acceptance risk.

For Blowpipe, the Check line's scale and dart quantities are independent components. We never infer either quantity from the other, from weapon capacity, from the commonly quoted one-third dart rate, or from animations. A dart-type change skips the ambiguous dart delta while retaining any independent measured scale decrease; an unsupported dart name fails closed. Unload resets the baseline because darts/scales can be returned rather than consumed. If any component price is missing, the whole measured spend is left unbooked and the new read becomes the baseline, avoiding partial or later duplicate booking. Costs use RuneLite's GE price for the exact component at the time the measured difference is booked.

For ordinary Tridents, the measured charge-count difference is converted using the known recipe: Seas uses one death rune, one chaos rune, five fire runes and 10 coins per charge; Swamp uses one death rune, one chaos rune, five fire runes and one Zulrah scale per charge. Rune/scale flows use RuneLite GE prices and coins use their measured face value. The standard recipes are documented by the [Trident of the seas](https://oldschool.runescape.wiki/w/Trident_of_the_seas) and [Trident of the swamp](https://oldschool.runescape.wiki/w/Trident_of_the_swamp) pages. Swamp's enhanced form uses the same measured component recipe. The enhanced Seas variant is deliberately unimplemented: its scale/coin charge mode is not present in the Check count, so charging mode cannot be inferred safely.

The source also records Trident charge dialogs such as `You add a charge to the weapon. New total: 2016` and generic uncharge confirmation messages. A future charge-dialog read may advance a baseline only when the successful numeric absolute total is linked to an exact supported Trident variant; a menu selection alone is only intent. An uncharge option or confirmation does not expose a numeric balance. It must not be interpreted as a zero balance and charged as a spend: uncharge can return unspent runes/scales, and the Seas dialog says coins are not returned. To support uncharge, the producer must correlate the confirmed result with the full measured returned-component quantities and mark those returns as ownership-neutral while advancing the baseline without a cost. That dialog-event/return matcher is not implemented; the current supported-item Uncharge action simply resets the Check baseline so a later read seeds rather than charging the returned balance. Blowpipe `Check` lines remain the only supported read surface for its separate scale/dart components; Unload likewise resets its baseline.

Between successful reads, a future UI may label the last observed balance as **unmeasured**. That display status must remain informational and cannot feed transactions or alter counts, types, prices or eligibility. No charge-balance row is currently shown in HUD+.

## Existing scaffold mapping

- `ChargeFamilyIds` remains the stable family identity layer. `ChargeRecipeCatalogue` records the recipe and an explicit implemented/unimplemented family status; only Blowpipe and Trident are active families, with supported variants enumerated in the parser (enhanced Seas stays off).
- A pure measured-read parser/state tracker replaces menu calibration as the authority. A fresh Check menu action supplies only target identity; one matching valid numeric read seeds it, and only a second read for the same target identity can produce booking-ready component deltas.
- `ChargeSpendBooking` and `GpManagerEngine.bookChargeSpend` accept only those measured deltas with component-level GE prices. They no longer accept arbitrary generic inventory losses behind a persisted family-calibration boolean.
- `LiveProducerBridge.tryBookChargeFromLosses` and `ChargeRecipeCatalogue.familyForChargeComponentLosses` are retired: both guessed a family from fungible losses, including Zulrah scales shared by several items, and the former has no live caller.
- Weapon Check/Configure menu clicks no longer calibrate charge accounting. Check actions only bind the following exact chat measurement to a target identity. Uncharge/Unload actions reset the measured baseline because returned components are not costs. A supported item-on-item load action arms bounded evidence for the selected component and stable target identity. When candidate losses settle without a quantity, all supported negative recipe components in that settle are held in one non-counted Review row rather than booked as ordinary costs. A later same-target Check may resolve only the measured load quantity from the previous Check, provided that baseline was at most the configured confirmation window old when the Review row was created; Blowpipe confirms scales only and leaves darts unmeasured. Tridents use their exact per-variant charge ratios. If fewer quantities are confirmed, a neutral transfer stores only that portion and residual flows remain Review. Multiple same-target candidate rows or duplicate same-id flows remain unresolved because a single measured increase cannot be assigned between them; no Check or an expired configurable 1–60 minute window (10 minute default) leaves the owner Review intact. A Check cannot resolve a row with a different target identity. Pending Review quantities block measured charge-cost booking for the same variant/component; confirmed neutral transfers no longer block later use costs. An owner correction remains available and counted owner decisions block overlapping automatic charge booking. Another menu action cancels the bounded load intent, and stronger bank/trade transfer evidence clears it. Inventory snapshots aggregate by item id: same-id source attribution inside one matching settle remains open for B05 acceptance. Utility-container Check/Fill/Empty evidence remains separate and continues using the existing container gate.
- No `AnimationChanged` producer is added. There is no probabilistic or estimated charge booking.

## Verification and limits

Offline tests cover exact Check parsing (including commas, one/zero/no darts), Check target matching and expiry, same-variant target changes, first-read baselines, measured decreases, equal/increased/invalid reads, scale decreases across dart-type changes, exact Trident recipes, load-to-Review settlement, no-Check retention beyond the window, same-target Check confirmation, partial scale confirmation with dart residual, full Trident recipe confirmation, multiple same-target rows and duplicate same-id flows staying in Review, owner correction, spend guards, Ledger-only presentation, and plugin wiring proving load and Check use the same stable target identity. Unload/Uncharge baseline resets, missing/incorrect prices and aggregate overflow remain covered. The B05 live matrix covers actual Check delivery/order, target-slot stability, reloads, component settlement timing, supported Trident variants and price availability. Charge/uncharge dialog receipts and “unmeasured” presentation are not delivered by this pass. Persistence of the last measured balance across plugin restart, deaths, and account changes is intentionally not claimed; a fresh first read after restart only seeds a new baseline.
